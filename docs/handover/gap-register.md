# Gap register — specification versus implementation

Baseline date: 2026-08-10

Compares the platform against its two source specifications and records what is
implemented, what is not, and what each remaining item needs. Every figure was
measured against the running system, not inferred.

Sources:

- `GRC_Data_Dictionary.xlsx` — 46 tables across 8 domains
- `Updated2_GenBioCa_Compliance_Platform 22June2026 (2).xlsx` — 30 sheets

### Why Controls and Checkpoints are empty in GENBIOCA

This looks like a failed import and is not one.

The workbook's `06_Framework_Checkpoints` is a **clause catalogue** — published
requirements shared by every company. The importer maps it to `framework_rules`,
which is why ISO 27001 carries 116 rules. All 340 landed.

The application's `checkpoints` entity is a different thing: a Company's own
control-testing schedule. Likewise `controls`. Neither exists in the workbook,
so neither could be imported. They are created in the application during
onboarding, once the Company decides which controls it operates.

**Action:** none required of the platform. Populating Controls and Checkpoints
is an onboarding activity with the client.

## 2. Data dictionary — 32 of 46 tables implemented

| Domain              | Missing tables                                                                 |
| ------------------- | ------------------------------------------------------------------------------ |
| CRM                 | `customer_master`, `company_customers`, `deals`                                |
| Operations          | `notifications`, `tasks`, `comments`, `report_runs`                            |
| Master Data         | `frequencies`, `evidence_types`, `evidence_requirements`, `report_definitions` |
| Evidence            | `evidence_versions`                                                            |
| KPI & Performance   | `kpi_mappings`                                                                 |
| Policies & Controls | `company_frameworks`                                                           |

### CRM is specified scope, not optional

`customer_master`, `company_customers` and `deals` appear in the signed data
dictionary. They are the foundation the prototype's Customer Master, Customer
Analytics, Attribution Reports and Deals Won/Lost screens were to sit on. Those
screens exist in the prototype as route metadata only — a title, section and
icon, with no table, fields or data model — so there is no design to build
against yet.

**Action:** agree the customer and deal model with the client, then build.
This is a module, not a screen.

### Four master-data tables are implemented as code

`frequencies`, `evidence_types`, `evidence_requirements` and
`report_definitions` exist as enumerations and application code rather than
tables. The behaviour is correct, but the Company cannot add a reporting
frequency or evidence type itself — it needs a code change and a release. The
dictionary clearly intended these to be configurable.

**Action:** decide whether client-configurable master data is required for V1.
If so, each becomes a table plus a small admin screen.

### Naming differs throughout

The dictionary and the implementation use different names for the same
concepts: `companies`/`tenants`, `regulatory_frameworks`/`frameworks`,
`regulatory_rules`/`framework_rules`, `capa_records`/`capas`,
`audit_logs`/`audit_events`, `upload_errors`/`import_batch_rows`,
`kpis`/`kpi_definitions`, `evidence_documents`/`evidence`.

**Action:** reconcile in documentation. Renaming 50 live tables to match a
document carries risk with no functional benefit.

## 3. Data removal and the right to erasure

The API exposes **four** delete routes in total: unlink evidence from a CAPA,
unlink evidence from a Gap, delete a KPI configuration, delete a KPI target.
Nothing else can be deleted — records are retired by status (`DISABLED`,
`ARCHIVED`, `CLOSED`) or soft delete (`deletedAt`, present on 18 of 50 models).

For a compliance platform this is mostly correct: an approval history that can
be erased is not an audit trail. Two cases must be separated.

**Offboarding — already works.** Setting a user to `DISABLED` ends their access
on the next request rather than at token expiry, because tenant context
revalidates user, membership and Company status on every authenticated call.
Their name remains on records they approved, which is what an auditor requires.

**Erasure — not implemented.** There is no way to redact a person's name, email
and phone while preserving the records they touched. DPDPA 2023/2025 and GDPR
are both in this Company's framework list, so a data subject request is
foreseeable.

**Action:** design pseudonymisation — replace personal fields with a tombstone
(`Former user USR-014`) while keeping identifiers and history intact. This is a
deliberate design task, not a delete button, and it must not be bolted on.

## 4. Other known gaps

Recorded in [known limitations](../known-limitations.md). Forward sequencing
(and what closed after the 2026-08-08 operable plan) lives in the
[completion plan](../status/completion-plan.md) as **V1.1 / V1.5 / V2**.

Still open at this baseline:

- no email or external notification delivery; in-app **My Work** and dashboard
  queues exist, but there is no notifications module or mail transport
- reports run on demand and export CSV; no scheduling, subscriptions or PDF
- PostgreSQL row-level security is not enabled; tenant isolation is enforced by
  application context, repository predicates, composite foreign keys and
  database triggers
- Playwright intercepts API responses, so no automated test crosses the browser
  to PostgreSQL
- production hosting, DNS, TLS, secret management and alerting are outstanding
- record comments and saved named views remain V1.1 strong additions

Closed after the prior operable plan (do not re-list as specification gaps):

- browser role assignment (`b8a5f94`)
- operational registers write UI and manual risk create (`14eeeaf`)
- register sort, URL-synced filters, My Work, evidence expiry surfacing
  (`6989c1e`)
- framework catalogue de-dupe for real compliance percentages (`413a4c5`)
- create Company from the UI (`80c8a3c`)
- grid KPI actual entry (`a1f37d9`)
- Gap Register bulk actions (`70989f2`)
- CAPA/Risk bulk actions, whole-row overdue cues, privilege access review
  (follow-on to V1.1 strong additions)

Administrator-controlled password recovery is intentional, not a gap.
